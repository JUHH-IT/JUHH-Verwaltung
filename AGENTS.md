# Entwicklungsregeln – JU Hamburg Finanzen

Alleiniger Entwickler ist Claude (seit 28.10.2026, Übernahme vom Codex-Pilot 0.5). Auftraggeber: Lennert Gust.

## Ort und Aufbau

- Basisordner: `~/Applications/JU Hamburg Finanzen/` (Programme). Quellcode mit Git in `Quellcode/`.
- Die App (`JU Hamburg Finanzen.app`) wird ausschließlich aus diesem Repository gebaut: `python3 mac/build_app.py --install ..`
- Daten liegen getrennt in `../Daten`, Sicherungen in `../Sicherungen`. Code darf nie in `Daten/` schreiben, außer über den Server (Ausnahme: Starter und Programmfenster ergänzen `Daten/programm.log`).

## Oberfläche (`static/js`)

- Aufbau nach Aufgabenbereichen (ab 0.31): Start (Aufgaben je Bereich, `views/overview.js`), **Mitgliederverwaltung** (`members.js` ohne Beträge, `klaerfaelle.js`), **Buchhaltung** (`bank.js`, `dues.js` Beitragseingänge, `cash.js`, `invoices.js`, `bills.js`, `open-items.js` mit OP-Listen, `journal.js`, `konten.js`), **Verband** (`budgets.js`, `rpj.js`, `auswertung.js`), **Verwaltung** (`settings.js` mit Reiter „Schalter“, ab 0.34 `benutzer.js` Benutzer & Rollen – nur Serverbetrieb). Neue Seiten in genau einen Bereich einordnen (`PAGES` in `main.js`) – Vorbereitung für Rollen (Mitgliederbeauftragte, Schatzmeister, Landesgeschäftsführung, Kreisverband, Systemadministration ohne Mitglieder-/Finanzdaten; noch nicht umgesetzt). Buchhaltungsfunktionen (Beträge, Zuordnen, OP-Listen) nicht auf Seiten der Mitgliederverwaltung anbieten und umgekehrt; Sprünge zwischen Bereichen über `go(seite, optionen)`.
- `main.js` Seitenleiste (dunkel, Farben `--side-*`), Anmeldung, Seitenwechsel; `store.js` einziger Zustand (`store`, `refresh`, `go`, Nachschlagehilfen); `api.js` Serveraufrufe mit CSRF.
- `html.js`: Vorlagen nur über `` html`…` `` – Werte werden automatisch maskiert; `raw()` ausschließlich für eigenes, festes Markup (Symbole). Nie Nutzer- oder Bankdaten per `innerHTML` oder `raw()` einsetzen.
- `format.js` nur Darstellung; verbindliche Betragsprüfung bleibt `formate.money` auf dem Server.
- `account-picker.js`: Kontenliste als Popup (Abschnitte Haushalt / weitere Konten / Bestandskonten). Kontierung (Buchungsplatz, Eingangsrechnungen, Budget-Umbuchung) immer mit EINEM Feld `postenField` + `bindPosten` (Titel ergibt sich, wie `haushalt.default_title`; Bestandskonten ohne Titel); übrige Kontofelder mit `accountField` + `bindAccountPickers`. Keine zweite Titelliste neben dem Konto.
- `rpj-field.js`: RPJ-Zuordnung (Projekt/Kostenart bzw. Mittelabruf) für Buchungsplatz und Eingangsrechnungen (`rpjField` + `bindRpj`, `rpjKind` wie `rpj.kind_of`). Für jede weitere Kontierung auf RPJ-Posten wiederverwenden.
- `gliederung.js`: Kreisverband/Ortsverband im Formular (`kvOvFields` + `bindKvOv`: Ortsverband nur aus dem gewählten Kreisverband), `ovLabel`/`ovById`. Für jede Auswahl von Kreis- und Ortsverband wiederverwenden.
- `ui.uploadProtected`: Importdatei als Vorschau hochladen; meldet der Server `password` (`required`/`wrong`), fragt ein Feld im Dialog nach dem Kennwort. Für weitere Importe geschützter Dateien wiederverwenden.
- `member-picker.js`: Mitgliedersuche als Popup (Kreisverband, dann Suche nach Name/Anschrift/Nummer/E-Mail; Sammelzahlung mit Beträgen; ab 0.29 „Person nicht in der Mitgliederliste“ und negative Beträge, `split: false` für genau eine Person; ab 0.31 „Unklar – Klärfall“ (`unclear`), Auswahl für den Server mit `membersPayload`). Für jede Mitgliederauswahl wiederverwenden, keine zweite Suche bauen.
- Popups (`overlay`, #preview) liegen über Dialogen (`dialog`, #modal); Esc und ⌘W schließen über `closeTop` immer die oberste Ebene. Öffnet eine Auswahl eine weitere Liste, zuerst die eigene schließen.
- `ui.js` Dialog, Hinweis, Tabelle, Kopf; `views/` je Bereich eine Datei (`bank.js` + `booking.js` Buchungsplatz, `budgets.js` + `kv.js` Haushalt, Kreisverbandsseite mit Budgetkonto, Werte-Dialog und Abgleich mit der Masterdatei, `members.js` Mitglieder mit Import und Mitgliedsdialog (`memberDialog` mit `preset`/`onSaved`, `account`), `dues.js` Beitragseingänge, `klaerfaelle.js` Klärfälle, `open-items.js` Offene Posten mit OP-Listen (`duesPanel`), `sepa-datei.js` SEPA-Datei einlesen, `auswertung.js` Auswertung, `cash.js` Kasse (nutzt den Buchungsplatz aus `bank.js` über `renderLedger`), `rpj.js` RPJ-Mittel (Projekte, Bescheid, Mittelabrufe, Einzelübersicht, Import, „RPJ zuordnen“), `konten.js` Kontenliste und Kontenblatt, `overview.js`, `imports.js` …).
- CSS-Klassen mit Bereichspräfix (`bank-item`, `row-*`, `kv-*`), damit Bereiche sich nicht gegenseitig verstellen. Farben nur über die Variablen in `css/app.css`.
- Der Server liefert nur Dateien aus `static/` mit erlaubter Endung aus (`app.static_file`, geprüft in `test_static.py`); CSP erlaubt nur eigene Skripte.
- Karte (ab 0.32, `views/karte.js`, `adressdaten.js`): Leaflet 1.9.4 liegt unverändert unter `static/vendor/leaflet` (Prüfsumme in `test_karte.py`; die Dateien haben Windows-Zeilenenden – `.gitattributes` schützt sie, Patches deshalb immer mit `git am --keep-cr` einspielen und den Baum-Hash vergleichen) und wird erst beim Öffnen der Karte geladen. Einzige Ausnahme in der CSP: Bilder von `https://tile.openstreetmap.org` (Kartenhintergrund, per Schalter `map_tiles` abschaltbar). Texte auf der Karte (Hinweise, Namen) nur als DOM-Knoten mit `textContent`, nie als HTML-Zeichenkette an Leaflet geben. Es gibt immer höchstens eine Leaflet-Karte: `leaveMap()` gibt sie frei – `main.js` ruft das bei jedem Neuaufbau der Seite. Suchtexte und Anschriften nur per POST an den Server (`/api/strassen-suche`, `/api/adresse-pruefen`), nie in der Adresszeile. Farben der Kreisverbände `--kv-5100` … `--kv-5700` (benachbarte Bezirke unterscheidbar, Namen stehen zusätzlich auf der Karte), Dichte `--map-seq-1…5`. Die Adressprüfung im Mitgliedsdialog (`bindAddressCheck`) ist nur ein Hinweis und darf das Speichern nie verhindern.

## Arbeitsweise

- Änderungen auf eigenem Branch, Merge nach `main` und Neubau der installierten App nur nach Freigabe durch Lennert.
- GitHub (ab 0.33, privates Repository – einzige gemeinsame Quelle, auch für mehrere parallel arbeitende Agenten):
  - Je Aufgabe ein eigener Branch und ein Pull Request; nie direkt auf `main` schreiben, nie selbst zusammenführen. Ein Pull Request nennt, was geplant, umgesetzt und getestet ist.
  - Freigegebene Version = Tag `v<Version>` auf `main`, erst nach Freigabe durch Lennert; `VERSION` in `app.py` nennt dieselbe Version. Einen übertragenen Tag nie versetzen oder löschen (der Server bricht dann ab) – stattdessen eine neue Version.
  - Die Datenregel gilt überall bei GitHub: Quellcode, Commit-Texte, Pull Requests, Issues, Kommentare, Protokolle der Tests – nur Anzahlen und Ja/Nein aus echten Daten, keine Bildschirmfotos mit echten Daten. Daten, Sicherungen, Belege, Kennwörter und Schlüssel werden nie übertragen; `test_repo.py` muss grün sein.
  - Neue Beispielwerte (IBAN, E-Mail) nur aus den in `test_repo.py` erlaubten nehmen; die Liste nicht um echte Werte erweitern.
  - Zugangsschlüssel (Deploy key des Servers, Tokens) liegen nur auf dem jeweiligen Gerät, nie im Repository oder im Chat.
- Vor jedem Commit: `python3 -m unittest discover` (alle `test_*.py`, alle grün).
- Bei Änderungen an der Oberfläche zusätzlich `node tests/html_escape.mjs` (Maskierung) und der Browser-Durchlauf mit erfundenen Daten: `NODE_PATH=$(npm root -g) node tests/ui_smoke.mjs <Ordner für Bildschirmfotos>` (benötigt Node, Playwright mit Chromium und die Python-Abhängigkeiten; startet einen eigenen Server in einem temporären Ordner).
- Neue Funktionen bekommen Tests. Geld immer in ganzen Cent; Beträge nur über `formate.money` lesen.
